# 代码与工程文档规范

## 语言与文本格式

开发说明、说明性注释、人工验证记录、提交说明、Issue、PR 和最终复审默认使用中文。代码标识符、文件名、API、命令、协议与机器可读字段保持准确原样。

文本保存规则由根目录 [.editorconfig](../.editorconfig)定义，Git 行尾规则由 [.gitattributes](../.gitattributes)定义。修改限于任务相关文件。遇到乱码或异常大的整文件差异，先核实终端编码、原始字节、`git ls-files --eol`、`git check-attr` 和 Git 的行尾配置，再决定是否改动文件。

## Astro、TypeScript 与 CSS

- 沿用现有代码的缩进、引号和命名方式。TypeScript 变量和函数使用 `camelCase`，类型和组件使用 `PascalCase`。路由文件名按公开 URL 组织，CSS 自定义属性使用能说明用途的短横线命名。
- 为组件输入和跨文件边界声明有意义的类型。对外约定或容易误用的代码按需说明输入、返回、默认值、副作用及失败行为。
- 注释解释设计理由、约束和边界，明显的代码行为由命名和结构表达。涉及行为变化时同步更新注释与直接受影响的文档。
- 共享视觉值优先复用现有设计 Token，页面布局和样式保持贴近使用处。出现实际复用需求时再抽取公共结构。

## 事实来源与长期记录

站点规格维护产品边界和验收，开发工作流维护工程门禁与交付，源码和配置描述实际实现。README 导航到专题入口。工程文档区分已实现、已确认规划和待验证事项。原型、实验或目标结构须标明适用范围和证据。

使用客观、非对话式语言，以行为、契约、验证或职责角色为主语。对重要的安全、权限、数据和 Git 历史边界使用明确约束。正式 Issue、PR、提交说明和最终复审省去“我”或“我们”等第一人称叙述，以实际职责称呼项目维护者。“用户”指产品的实际使用者。具体工具职责可在 [AI 协作入口](../AI_CONTEXT.md#协作职责)准确描述。正式记录应能脱离会话独立理解。PR 与最终复审围绕目标、变更、验证、风险和后续事项。正式证据引用使用可长期访问的仓库文件、提交、Issue、PR 或验证记录，本机绝对路径、临时补丁、内部审核轮次及无法长期访问的资料留在临时交接中。PR 的内容及复审门禁见[开发工作流](WORKFLOW.md#pull-request)。

## Markdown 审校

- 使用稳定、语义明确的标题，按主题组织层级。普通段落一段一行，列表、代码围栏和表格按结构换行。
- 新增或修改 Markdown 后完整复读，核对受众、术语、事实状态、标题、段落、列表缩进、表格列数、围栏、内部链接及文本格式。
- 清理仅服务于某次提示词、临时授权、对话或审查过程的内容。需要保留的历史事实注明时间、适用版本与背景。
- 当事实、链接或维护职责实际变化时更新所属文档。跨文档治理按[文档同步](WORKFLOW.md#文档同步)处理。
